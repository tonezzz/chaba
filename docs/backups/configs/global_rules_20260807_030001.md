# Global Sub-Agent Usage Guidelines

## Core Principles

### When to Use Sub-Agents
Sub-agents are powerful tools for specific situations. Use them when:

1. **Parallel Execution**: Multiple independent tasks can run simultaneously
2. **Complex Exploration**: Broad, uncertain searches across codebases
3. **Multi-Step Tasks**: Self-contained work with many interdependent steps
4. **Context Isolation**: Work unrelated to current task to keep context clean
5. **Background Processing**: Long-running tasks while continuing other work

### When NOT to Use Sub-Agents
Avoid sub-agents for:

1. **Single Operations**: One-off file reads, simple edits, single commands
2. **Known Paths**: When you already know the exact file or function location
3. **Simple Questions**: Quick answers you can provide directly
4. **Sequential Dependencies**: Tasks that must run in order (chain in one agent)
5. **Overhead-Heavy**: Tasks where sub-agent setup cost exceeds benefit

## Sub-Agent Profiles

### subagent_explore (Read-Only)
**Purpose**: Codebase exploration, research, search without modifications

**Tools Available**: grep, glob, read, web_search, mcp_call_tool

**Use Cases**:
- Finding code patterns and architecture
- Tracing dependencies and relationships
- Researching implementation approaches
- Understanding existing conventions
- Impact analysis for changes
- Documentation research
- Using MCP tools for enhanced search (e.g., docs MCP server for documentation search)

**Example**:
```
"Research how authentication is implemented across the codebase.
Look at middleware, routes, and database models.
I need to understand the auth flow to plan a new feature.
This is read-only - do not make changes."
```

### subagent_general (Full Access)
**Purpose**: General-purpose tasks requiring write access or command execution

**Tools Available**: read, write, edit, exec (and more)

**Use Cases**:
- Multi-step feature implementation
- Parallel infrastructure operations
- Complex testing and verification
- Configuration updates across files
- End-to-end workflow testing
- Background processing tasks

**Example**:
```
"Implement a new user settings feature following existing patterns.
Update models, API routes, and frontend components.
Add tests and update documentation.
Make all necessary changes directly."
```

## Best Practices

### 1. Front-Load Context
Sub-agents are stateless and cannot ask clarifying questions. Provide:
- Relevant file paths and directories
- Function/class names to investigate
- Existing patterns to follow
- Project-specific conventions
- Exactly what you need back

### 2. Be Specific About Scope
- Define the boundaries of the task
- Specify if it's read-only or implementation work
- Set expectations for thoroughness level
- Mention any constraints or requirements

### 3. Choose the Right Profile
- Use `subagent_explore` for research and investigation
- Use `subagent_general` for implementation and changes
- Use `is_background=true` for parallel work or long tasks
- Use `is_background=false` when you need the answer before continuing

### 4. Parallel Execution Strategy
- Launch background sub-agents in parallel for independent tasks
- Use foreground sub-agents when sequential work is needed
- Don't launch multiple foreground sub-agents simultaneously
- Launch background sub-agents first, then foreground if needed

### 5. Trust but Verify
- Generally trust sub-agent results
- Review changes for consistency and quality
- Run verification steps (tests, lint, build)
- Only redo work if something looks wrong

## Communication Patterns

### Good Delegation Example:
```
"Investigate the error handling patterns in the API layer.
Look at src/api/ directory, focusing on middleware and route handlers.
I need to understand how errors are caught, logged, and returned to clients.
This is research only - do not make any changes.
Be thorough - check all API-related files."
```

### Bad Delegation Example:
```
"Look at the API code and tell me about it."
```
(Too vague, no scope, no specific goal)

## Project-Specific Guidelines

Check for project-specific sub-agent guidelines in:
- `AGENTS.md` in the project root

- Project documentation for workflow patterns

Respect project-specific patterns over these general guidelines when they conflict.

## Common Anti-Patterns

### 1. Over-Delegation
```
❌ "Read this file and tell me what it says"
✅ Read the file directly
```

### 2. Under-Specified Tasks
```
❌ "Fix the authentication bug"
✅ "Investigate the authentication bug in src/auth/login.py.
   Users report 403 errors on valid credentials.
   Check database queries, JWT validation, and middleware.
   This is read-only research first."
```

### 3. Sequential Parallel Tasks
```
❌ Launching multiple foreground sub-agents for dependent work
✅ Chain dependent work in a single sub-agent or run sequentially
```

### 4. Ignoring Project Context
```
❌ Generic research without project-specific conventions
✅ "Research auth patterns, following the existing middleware structure
   in src/auth/ and the JWT patterns used in other routes"
```

## Verification After Sub-Agent Work

1. **Review Changes**: Check for consistency with project patterns
2. **Run Verification**: Tests, lint, typecheck, build as appropriate
3. **Test Functionality**: Verify the changes work as expected
4. **Update Documentation**: Update docs if behavior changed
5. **Commit Changes**: Use proper commit messages

## Continuous Improvement

These guidelines should evolve based on:
- What patterns work well for your workflow
- Project-specific needs and conventions
- Lessons learned from sub-agent usage
- Changes in tool capabilities or best practices

Update this file when you discover better patterns or when current guidelines don't match your experience.
