# Dispatch outcome — board-api-write-latency (OPS-1314)

## What was found
The minutes-long `POST /comment|/action` stalls on idc03 were caused by
`/tmp/board-api.lock` hold time, not rendering (render was already async on
its own lock). In weight order: (1) `git-safe-pull.sh` held the same flock
across its entire pull/rebase/autostash/reconcile phase — 1-6 min when
upstream moved, and every checkout's pull took the served checkout's lock;
(2) board-api's immediate `git add+commit` per write inside the lock
(~10-20s, `BOARD_API_COMMIT`); (3) `hide_dispatch_session` and
session-delivery ran SQLite/SSH under the request lock; (4) no dedupe —
timed-out clients retried and double-posted. `GET /cards` never took the
lock and stayed fast; the thread pile was a symptom of the holds.

## What changed
`scripts/board/board-api.py`: bounded `LOCK_NB` acquire on every lock site —
card writes, `/ready`, remote-backed paths, `_pub_board_send` — returning
HTTP 503 **before** any mutation after `BOARD_API_LOCK_WAIT_S` (25s default;
75s for the WP lock), so a retry can never double-apply; lock wait/hold
logged when >5s; SSH/session side effects moved to a post-write daemon
queue (handler snapshots card id + action, releases, worker appends comms
via a second short locked write); `/comment` dedupe — `request_id` stamps
the comm's `req` field and dedupes forever, same `(from,text)` within
`BOARD_API_COMMENT_DEDUP_S` (120s) dedupes, `dedupe:false` bypasses,
duplicates return `{deduped:true}`; handler socket timeout 120s; startup
writes the served-checkout realpath to `/tmp/board-api.lock.repo`.
`scripts/git-safe-pull.sh`: reads that sentinel and skips the shared board
lock when pulling a different checkout; lock-wait and pull-phase durations
logged ≥5s with held/not-held. Served-checkout ordering (render lock →
board lock) unchanged; absent sentinel = conservative.

## Result + verification
- `python3 -m py_compile` clean; `board-api.py --selftest` ok;
  `tests/test-kanban-commit.sh` 59/59.
- Sandboxed HTTP smoke (temp repo): 3 POSTs → 1 comm entry (request-id and
  window dedupe both return `deduped:true`); held `/tmp/board-api.lock` →
  POST returned 503 in ~3s (`BOARD_API_LOCK_WAIT_S=3`); write after release
  → 200.
- Live idc03 board-api was itself saturated during the session — progress
  curls timed out; card comm + job record were written directly to the
  worktree instead (safe per the card's workaround note; card-union merges).
- Production verify after deploy: journal lines
  `board-api lock wait >Ns ... — 503` and no new duplicate comms.
- Job record: `docs/ssot/jobs/kanban/2026-11-17-board-api-lock-latency.yml`;
  card comm appended to `board-api-write-latency`. Committed on the session
  branch; not pushed, not deployed (restart of chaba-board-api required for
  the fixes to take effect — production still runs the old code).
