# dispatch-outcome — board-api-wedged-8min-on-hung-outbound-h-389be8 (KNB-1371)

## What happened (2026-11-25 ~09:59–10:07, idc03)

`chaba-board-api` (pid 767125) held FLOCK WRITE on `/tmp/board-api.lock`
AND `/tmp/board-api-wp.lock` with an ESTABLISHED outbound HTTPS
connection to 103.99.11.249:443 — the h3 Plesk host serving the WP /
MediaWiki origin (213KB sent, no response). All 51 threads parked in
`futex_wait`; `GET /cards` and `/health` timed out ~8min until manual
`systemctl --user restart`.

## Root cause

Two compounding defects, both in the write path:

1. **No total deadline on outbound work.** Every urllib call already
   has a per-socket-op timeout (20–45s), but that is not a deadline:
   a slow-drip peer, or a sequential fan-out — `/publish` drains the
   *entire* outbox synchronously, `/lesson` chains wp+wiki+mddb — can
   hold `WP_LOCK` for minutes or indefinitely.

2. **Unbounded blocking `fcntl.flock` in-process.** `render()` took
   `/tmp/board-render.lock` with `flock(LOCK_EX)` (contended by
   git-safe-pull pull phases, 1–6min) and `publication.py`'s
   `JsonSink.publish`/`Outbox._append` used blocking `LOCK_EX` on
   ledger appends. On py<=3.13 `fcntl.flock` holds the GIL while
   blocked — one contended flock freezes *every* thread, which
   explains `/health` (lock-free) dying too. (Verified on this host:
   py3.14 flock does NOT hold the GIL; idc03's unit runs an older
   python where it does.)

## What changed

`scripts/board/board-api.py`
- `acquire_lock()` returns a `_TrackedLock`; all held flocks recorded.
  Daemon watchdog (`BOARD_API_LOCK_WATCHDOG_S=5`) dumps all thread
  stacks via faulthandler to the journal once per hold episode past
  `BOARD_API_LOCK_HOLD_ALERT_S=120`. `/lock-stats` now exposes
  `held_now` + `lock_hold_alert_s`.
- `render()` takes the render flock via bounded `acquire_lock`
  (`BOARD_API_RENDER_LOCK_WAIT_S=30`); busy lock → skip the pass
  (60s render timer is the backstop).
- `REMOTE_WRITE_PATHS` dispatch extracted to `_remote_dispatch()` and
  wrapped in `pub.run_bounded(REMOTE_WRITE_DEADLINE_S=300)` → 504 on
  expiry; orphan finishes lock-free, upsert semantics converge.
- `do_publish` piggyback drain bounded by `PUB_DRAIN_BUDGET_S=60`
  (`op:"drain"` gets 300).

`scripts/board/publication.py`
- `run_bounded(fn, timeout_s, label)` — daemon-thread total-deadline
  wrapper raising `DeadlineError`.
- `PUB_SINK_DEADLINE_S=240` wraps every `sink.publish` in
  `publish_event` and `Outbox.drain` — one hung sink lands in the
  outbox like any `DeliveryError`.
- `Outbox.drain(budget_s=)` caps entries launched; deferred stay
  pending (`res.deferred`).
- `_flock_bounded` (LOCK_NB + 10s) replaces unbounded `LOCK_EX` in
  `JsonSink.publish` and `Outbox._append`.

Tests: `DeadlineTest` in `tests/board/test_publication.py`
(run_bounded timeout, hung sink → queued + outbox, drain deferral,
bounded flock); board-api `--selftest` covers hold tracking, watchdog
single-dump, render busy-skip.

## Follow-ups (not done — separate processes, same pattern)

`board-render-guard.py:83`, `request-sweep.py`, `merge-sweep.py`,
`kanban-dispatch.py`, `answer-sweep.py`, `review-digest.py`,
`deploy-preflight.py` still use unbounded `flock(LOCK_EX)` — they are
short-lived separate processes so they can't freeze board-api, but the
same bound applies if any moves in-process. Post-deadline orphan
remote-dispatch threads can overlap a retry — converges via
upsert/idempotency; watch `delivered.jsonl` if 504s become common.

lessons:
- urllib timeout= is per-socket-op, not a deadline — slow-drip peers and sequential fan-outs need an outer run_bounded-style wrapper.
- fcntl.flock(LOCK_EX) holds the GIL on py<=3.13 — an unbounded flock in a threaded server freezes every thread incl. lock-free endpoints; always LOCK_NB + retry deadline in-process.
- /publish's piggyback outbox drain made WP_LOCK hold time = backlog × per-sink timeout — bound both the per-sink call and the drain loop.
- A mid-session compaction commit can sweep uncommitted work into HEAD — verify `git status`/`git diff HEAD` before assuming edits are still pending.
