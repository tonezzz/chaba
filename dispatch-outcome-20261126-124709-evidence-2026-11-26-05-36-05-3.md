# Dispatch outcome — health-monitor-config-playlived-postgres

## What was found (the card's premise was partly wrong)

- **mcp-health runs ON tony-dell.** Devin's MCP config spawns it via
  `ssh tony-dell ... node server.js` from `~/CascadeProjects/chaba-tony-dell/mcp-servers/mcp-health`.
  So `url: http://127.0.0.1:9230/sessions` for Playlived (tony-dell) is already correct —
  127.0.0.1 IS tony-dell. The FAIL is a **real outage**: `playlived-dell.container` is
  `failed` (podman create dies on `conmon failed: exit status 1` /
  `k8s-file doesn't support --log-tag`, restart counter maxed ~11:56 +07).
  curl → rc=7 in ~10ms. Repair needs a host service restart → approval requested on the card.
- **Postgres FAIL was a monitor bug, not an outage.** Canonical
  `chaba-postgres-16` is on idc03 (up 2 days, healthy). A staged-but-uncommitted edit on
  tony-dell's readonly mirror already pointed the health entry at `host: idc03`; master
  still said `host: tony_dell` (whose same-named container is a frozen leftover — last
  health_checks write 2026-11-16). Root cause of the FAIL: tony-dell's `~/.ssh/config`
  has `Host idc03 → ProxyJump tony-omen`, and today's scoped-SSH hardening
  (`AllowTcpForwarding no` fleet-wide) refuses the direct-tcpip channel ProxyJump needs
  → `channel 0: open failed: administratively prohibited`. Direct ssh works fine.
- **get_health_status timeout**: not reproduced — returns 130 services normally; likely
  transient MCP-client timeout under load. health_checks rows are only written by
  `check_health`/`check_group`, and nothing scheduled runs them, hence the ~29h stale
  `last_checked`.
- **Bonus bug**: `get_troubleshooting_info` looked up health_checks by the raw requested
  id (`postgres`) while rows are stored under `service.name` (`Postgres`) → null
  last_checked. Fixed.
