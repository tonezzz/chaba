# dispatch-outcome — board-api-lock-contention (OPS-0725)

Session: `dispatch/20261120-181845-symptom-2026-11-17-18-20-ict-i` (attempt 2)

## Root cause (measured, not guessed)

The card flock `/tmp/board-api.lock` convoy on idc03 was NOT the render
pipeline — that was already async on `/tmp/board-render.lock` (60bd8a2769).
Live journal phase timings (`wait=/held=/load_ms/save_ms/card_path_ms`)
pinpointed three in-lock costs, all confirmed on the served checkout TODAY
(Nov 20, still failing):

1. **`card_path()` drift scan** — on any id/ref miss it safe-loaded ALL
   ~1,018 live cards + ~713 archived while holding the flock:
   `card_path_ms=59598` (one 60 s hold, dozens of writers queued behind it).
2. **Pure-Python YAML round-trip in `save()`** — `yaml.safe_dump` +
   `safe_load` re-parse on every write; the 194 KB card produced
   `save_ms=4787–10434` (up to 16 s on Nov 17). Every `/comment` and
   `/action` pays it — they serialize the whole card.
3. **`git cherry` per dispatch branch in `render-board.py`** — 236 dispatch
   branches × a patch-id recomputation over ~109k upstream commits =
   15–42 s EACH. Render took ~53 s and, because the render unit's flock fd
   was inherited pre-fix, it could also pin the card flock.

The 503s were the convoy's tail: each slow holder queued every other
writer past the 25 s acquire deadline (journal: 179 lock-wait lines in
24 h, max hold 102.7 s on `/comment`).

## What changed (this worktree)

### scripts/board/board-api.py
- `_YAML_LOADER`/`_YAML_DUMPER` constants — `yaml.CSafeLoader` /
  `yaml.CSafeDumper` when libyaml is present (it is on idc03), Safe*
  fallback otherwise.
- `load()`/`save()` now use the C pair → the 194 KB card's save drops
  from ~5–16 s to <100 ms.
- `card_path()` id/ref drift lookup replaced the full-corpus YAML scan
  with cached raw-text indexes (`_live_index`/`_archive_index`):
  regex-scan `id:`/`ref:`/`stem` fields only, TTL 120 s + directory
  signature invalidation (survives atomic renames + external writers).
  First-found semantics preserved; verified equivalent against the old
  scan on the real corpus (only pre-existing duplicate refs OPS-0087 /
  OPS-1038 differ, both benign).
- `_ref_seed()` now scans raw `ref:` lines instead of safe-loading all
  cards.

### scripts/board/card_io.py
- `atomic_dump_card()` uses the same C loader/dumper pair — covers every

## Lock architecture (verified, not changed)

- Card writes: `/tmp/board-api.lock` (bounded 25 s acquire → 503).
- Renders: async worker + `threading.Event` coalescing on
  `/tmp/board-render.lock` — never holds the card flock; response is
  sent before commit/render enqueue.
- WP-backed endpoints (`/lesson`, `/job`, `/report`): separate
  `/tmp/board-api-wp.lock`; slow WP calls can't stall card writes.
- `git-safe-pull` holds render→board only when a pull is actually needed
  and only for the checkout the locks protect (`.repo` sentinel);
  bounded 60 s acquire, then proceeds lock-free if wedged.
- Telemetry: `/lock-stats` per-endpoint wait+hold histograms, timeout
  counts, maxima (landed 60bd8a2769, confirmed live).

## Residual risk (documented, not blocking)

- `dr.classify_lane` can spend up to 30 s on a localhost jevos HTTP call
  inside the queue path under the flock (BOARD_CLASSIFY_AT_QUEUE=1,
  keyword-first so rare). One `mutate_ms=7289` in today's journal is
  likely this. Hoisting it out of the lock would break the atomic
  lane-stamp-with-queue contract — noted for a follow-up card if it
  recurs after this lands.

lessons:
- phase-timed lock logs (wait/hold/load/save/card_path) turn "lock
  contention" from guesswork into a ranked list — check them before
  touching code.
- PyYAML pure-Python dump+re-parse of ~200 KB cards costs 5–16 s; with
  libyaml it's <100 ms — always use CSafeLoader/CSafeDumper on write
  paths that hold a shared flock.
- `git cherry` rebuilds the upstream patch-id set per call; over a 109k-
  commit range that's ~15–40 s per branch — cache the set incrementally
  instead.
- Test sandboxes that clone a seeded repo silently break when prod code
  gains a new repo-internal import (REPO/scripts/board) — seed it.
- Duplicate `ref:` values can legitimately exist in the corpus; index
  lookups must keep first-found semantics, not assume uniqueness.
